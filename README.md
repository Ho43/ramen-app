# ラーメン記録

食べたラーメンを記録する、iPhone向けのWebアプリ（PWA）です。
HTML / CSS / JavaScript だけで作っているので、ビルドやインストールは不要です。

## デザインの決めごと

- テーマは「黒い丼の中」。墨色の背景に、卵黄のオレンジと朱色の雷紋
- マスコットは「ギルチキ」。絵は `giruchiki.png` の1枚だけで、点数に応じた違いは傾き・跳ね・きらきら・背後の光（CSSの `.chiki-t0` 〜 `.chiki-t3`）で表している
- 95点以上は「ギルティ」扱い。`app.js` の `GUILTY` を書き換えれば基準を変えられる
- 写真は選んだあと正方形に切り抜いて保存する（`app.js` の `cropImage()`、書き出しは一辺 `CROP_OUT` px）。倍率1で写真全体が枠に収まり、拡大すると好きな範囲を選べる
- カレンダーは前月・当月・翌月の3枚を横に並べた帯（`.cal-track`）を動かしている。指に1対1で追従し、画面幅の18%動かすか素早くはじくと切り替わる（`setupSwipe()`）
- ホームのセリフは `app.js` の `chikiTalk()`。点数に応じた `TIER_TALK` の3つに、連続記録・店の来店回数・通算杯数・時間帯で当てはまるものを足し、その中からランダムに1つ選ぶ（優先順位はつけていない）
- 話題にする一杯は、記録した直後だけその一杯（`lastSavedId`）。それ以外は最近の10杯から毎回選び直すので、開くたびに変わる

## 身内向けの共有機能（Firebase）

- Firebaseの部品（`https://www.gstatic.com/firebasejs/...`）は、Service Worker（`sw.js`）が別枠のキャッシュ（`FIREBASE_CACHE`）で一度取れたら使い回す。URLにバージョン番号（`12.0.0`）が入っていて中身が変わらないため、キャッシュしたままで問題ない。バージョンを上げるときはURL自体が変わるので、自動的に新しいものを取りに行く
- アカウント画面の「確認しています…」が8秒以上続いたら、電波の案内と「もう一度試す」ボタンに切り替わる（`renderAccount()` の `slowTimer`）

- ログインとデータの置き場所にFirebaseを使っている。`firebase-config.js` に接続情報、`cloud.js` にやり取りの関数をまとめてある
- 記録そのものは今まで通り端末の中（IndexedDB）に保存する。共有は記録ごとに選ぶ方式で、記録画面の「記録と同時にみんなへ共有する」か、編集画面の「みんなに共有」を押したものだけがFirebaseに送られる
- 同時共有のチェックの状態は `shareByDefault` に覚えていて、次に記録するときの初期値になる
- 住所はお店ごとの情報として `shops` に持たせている。新しいお店を作るときに入力でき、あとからお店の詳細画面でも登録・変更できる。地図は店名と住所を合わせてGoogleマップの検索URL（`mapUrl()`）に渡している。共有すると投稿にも住所が入り、みんなの記録から直接地図を開ける
- 写真は長辺720pxに落としてから文字列にして送る（Firestoreは1件1MBまでのため）。共有した記録にはローカル側で `postId` を持たせ、共有中かどうかを覚えている
- 投稿やコメントに書き込まれた名前・アイコンは投稿した時点のもの。表示するときは `profileCache` に読み込んだ最新のプロフィールを優先するので、あとからアイコンを変えても過去の投稿に反映される
- ギルティボタンは朱色の判子（`.gb-stamp` に明朝体の「罪」）。押して付けたときだけ、まわりにきらめきが飛ぶ（`.is-burst`）。外したときは光らない
- ギルティ（いいねの代わり）は投稿の `guiltyUids` 配列。押した人のuidを出し入れするだけで、数は配列の長さ。ルール側で「自分のuid 1件の増減だけ」に制限している
- コメントは `posts/{id}/comments`。消せるのは書いた本人のみ
- みんなの記録の一覧にはコメント数を出す。投稿の `commentCount` を、コメントを書いたとき・消したときに1つずつ増減させている（ルール側で「1増えるか1減るか」だけ許可）
- コメントは1段だけ返信できる（`parentId`）。コメント自体にもギルティを付けられる（コメントの `guiltyUids`）
- 投稿のアイコンや名前を押すとその人のページに飛ぶ。相手の端末の中身は見られないので、図鑑とカレンダーは「その人が共有した記録」から組み立てている
- 公開設定はプロフィールの `showZukan` / `showCalendar`。決めていない人は見せる扱い
- 新しい記録の書きかけは `draft` に覚えていて、別の画面に移って戻っても続きから書ける。記録し終えたら空になる
- 名前バッジは共有した記録の数（`cloud.getPostsByUser()` の件数）を基準にした達成度バッジ。`BADGES` に9段階（箸1〜3・れんげ1〜3・丼1〜3）を定義してあり、`BADGE_STEP`（5杯）ごとに1段階解放される。絵がまだ無いものは `file: null` にしてあり、一覧では「準備中」と出て選べない。絵が用意できたら `file` にファイル名を入れ、`sw.js` のキャッシュ一覧に足すだけで使えるようになる
- 次のバッジまでの進み具合は `badgeGauge()` のゲージ（n/5）。ゲージはオレンジから赤への斜めのグラデーションで、右端に次に手に入るバッジを薄く置いてある。横の「詳細」から `#/badges` のバッジ一覧へ行き、そこで表示するバッジを選ぶ（`profile.badgeChoice`）。共有して区切りに届くと `badgeFlash()` の演出が出る（95点のギルティ！と同じ流れ）。共有を減らして解放段階が下がった場合は、選んでいた段階が自動でその時点の解放段階に収まる。名前の横に出るのはプロフィール画面のみ（一覧・コメントでは小さすぎて識別しづらいため見送った）
- ガチャの排出率は `RARITY_WEIGHT`。★3は3%まで下げてある
- 設定画面のコード入力欄はテストプレイ用。`REDEEM_CODES` に書いたコードを入れるとポイントがもらえる（1人1回、使用済みは `chikiState.redeemedCodes` に記録）
- 餌やりでもらえるポイントは `FEED_REWARDS`（1/3/5/10/15/30/100ptの重み付き抽選）。ガチャは1回 `GACHA_COST`（30pt）
- 投稿詳細には、自分の投稿だけ「この投稿を削除」ボタンが出る。端末側の記録が残っていなくても消せる（`clearLocalPostLink()` が、端末に紐づく記録が見つかった場合だけ共有中の印を外す）
- コメントアイコンは `?comment=1` を付けて投稿詳細へ飛ばし、詳細画面はそれを見て最初からコメント欄を開く。写真はどの画面でも押すと直接 `openPhoto()` の拡大表示になり、投稿本文への遷移とは独立させてある
- ギルチキへの餌やり・ポイント・ガチャは端末の中だけの遊び要素で、Firebaseには送らない。`db.js` の `chiki` ストア（バージョン2で追加）に1件だけ保存する。ホームのあいさつ欄が餌やりボタンを兼ねていて、1日1回ランダムなポイントがもらえる。ポイントでガチャ（`#/gacha`）を引くと衣装が手に入り、着せ替えるとマスコットの絵にSVGの衣装が重なる（`COSTUMES` / `costumeOverlay()`）
- ホームを一番下まで送ったあと、さらに上へ引き上げるとみんなの記録へ移る（`enableHomeSwipeUp()`）。ログイン済みのときだけ反応し、ふだんの縦スクロールとぶつからないよう、画面の一番下にいることを条件にしている。必要な距離は戻る操作より長め（150px）
- `#app` には `min-height: 100vh` を入れてある。中身が短い画面（図鑑など）でも、画面下半分からスワイプ操作を受け取れるようにするため
- 「戻る」は、実際に通ってきた画面へ戻す（`trail` / `trackVisit()` / `goBack()`）。履歴の項目それぞれに通し番号（`history.replaceState` の `at`）を振り、`trail[番号]` にそのとき見ていた画面を覚えておく。戻るときは `history.back()` を使うので、端末の「戻る」やブラウザの履歴ともずれない
  - 以前は画面ごとに決めた「ひとつ上」（`parentOf()`）へ戻していたため、ホーム → 自分のプロフィール → フォロー中 → 相手のプロフィール と進むと、戻るときに「みんなの記録」へ飛んでしまっていた
  - 戻るボタンの表記は戻るさきの画面の名前（`screenName()` の対応表。お店のように見出しがそのつど変わる画面は、`trailTitle` に覚えておいた見出しをそのまま使う）
  - 通知やブックマークからその画面を直接ひらいたときは通ってきた道すじがないので、`header()` に渡した `back` / `backLabel`（画面ごとに決めた行き先）を使う。リンク（`<a>`）で出るか、戻れるときはボタン（`data-action="back"`）で出るかもここで変わる
  - 画面を出さずに別の画面へ移すとき（記録が見つからないときなど）は `goReplace()` を使う。`location.replace()` を直接呼ぶと、その画面が道すじに残って「戻る」で行き止まりになる
  - 進む・戻るのどちらの動きを見せるかも、この通し番号が減ったかどうかで決めている（以前の `parentOf()` / `depthOf()` は不要になったので消した）
- スワイプで戻る先は、左上の「戻る」ボタンと同じ `backTarget` を使う（`header()` が呼ばれたときに入り、画面を切り替えるたびに router が空に戻す）。通ってきた道すじがあるときは `'history'` が入り、スワイプもボタンも同じ `goBack()` を通る
- 右へスワイプすると、ひとつ前に見ていた画面に戻る（`enableSwipeBack()`）。指に1対1で追従し、画面幅の22%動かすか素早くはじくと確定する。ホームと記録の画面では切ってあり、カレンダーでは日付の下の区切り線より下だけで反応する（月送りと分けるため）。登録は起動時の1回だけ。端末やブラウザ自身の「スワイプで戻る」が先に動くことがあるので、流し終えたときにURLが変わっていたら重ねて戻さない（2画面ぶん戻るのを防ぐ）。あわせて CSS で `overscroll-behavior-x: none` も入れてある
- ギルティボタンを長押しすると、押した人の一覧が出る（`setupLongPress()` と `showGuiltyList()`）
- スマホへの通知（プッシュ）は未実装。Firebaseのサーバー側から送る仕組みが必要で、無料のSparkプランでは使えないため。代わりにホームの「みんなの記録」へ未読件数を出している。最後に見た時刻は `localStorage` の `ramen-log:feed-seen` に端末ごとに持つ
- 人ごとのお知らせのオンオフは、自分のプロフィールの `mutedUids`。切った相手の共有は未読件数に数えない
- 共有された記録の詳細では、写真を押すと画面いっぱいに開く（`openPhoto()`）。2本指でつまむと拡大、2回たたくと等倍と拡大を行き来する
- 画面の切り替えは `page-in` / `page-back`、ボタンを押した感触は `is-pop`。Androidは `navigator.vibrate()` で振動するが、iPhoneはWebに振動の仕組みがないため動きだけで伝える
- 一覧には最新のコメントを1件出す。投稿の `lastComment` に書いておき、一覧を開くたびにコメントを読みに行かなくて済むようにしている
- 「一緒に食べた人」は投稿の `withUids`（相手のuidの配列）。記録画面で身内の一覧から押して選ぶ（`.with-chip`）。端末側の記録にも同じ `withUids` を持たせてあるので、あとから編集画面で共有し直しても選んだ人が残る
- 選ぶ相手の一覧は `cloud.getMembers()` で `users` をまるごと読んで作り、`memberCache` に覚える。新しい人が入ったときはアプリを開き直すと読み直しになる。自分は選べないよう一覧から外してある
- プロフィールの「一緒に食べた記録」は `cloud.getPostsTaggedWith()`。`withUids` への `array-contains` の検索で、配列は索引が自動で作られるため追加の設定は要らない
- 一緒に食べた人の名前とアイコンも、投稿時のものではなく `profileCache` の最新を使う（`avatarFor()` / `nameFor()` に uid だけ渡している）
- 共有済みの記録を編集すると、みんなの記録の側も書き換わる（`cloud.updatePost()`）。書き換えるのは店名・住所・食べたもの・日付・点数・コメント・一緒に食べた人・写真だけで、投稿者・投稿日時・ギルティ・コメント数には触らない。押されたギルティが消えたり、一覧の順番が変わったりしないようにするため
- 版の確認は、GitHubに置いてある `sw.js` を直接読んで `CACHE_NAME` を取り出し、`app.js` の `APP_VERSION` と比べている（`latestVersion()`）。**新しい版を出すときは、`sw.js` の `CACHE_NAME` と `app.js` の `APP_VERSION` の両方を同じ値に上げる**こと。片方だけだと更新に気づけない。設定画面の「アプリの更新」からも同じ確認ができ、新しい版があれば同じ更新の画面が出る
- 更新は `applyUpdate()`。ためてある古いファイル（キャッシュ）を先に消してから Service Worker を入れ替えて開き直す。消さずに開き直すと、`sw.js` が「まずキャッシュを返す」ので1回ぶん古いままになり、押したのに変わらないように見えていた。Firebaseの部品のキャッシュだけは中身が変わらないので残す
- `sw.js`は、キャッシュにあるファイルをまず返して画面を出し、新しいファイルは裏で取り直してキャッシュを入れ替える（stale-while-revalidate）。そのため、更新したファイルが実際に使われるのは次に開いたときから。HTML・JS・CSSの取り直しだけは、ブラウザ自身のキャッシュも無視して本当にネットへ行く（`cache: 'no-store'`。GitHub Pages側のキャッシュ指定に邪魔されて更新に気づけないことがあったための対策。`alwaysFresh`の判定）
- 以前は毎回ネットから取り直すまで画面を出していなかったため、電波が弱いと起動のたびに`app.js`（約200KB）と`style.css`の待ち時間が発生していた。更新に気づく仕組みは起動時の帯と設定の「アプリの更新」が別に持っているので、先にキャッシュを出しても更新は届く
- Firebaseの部品（アプリ本体・ログイン・データベース・通知）は`cloud.js`の`core()` / `store()` / `messaging()`で、**使うときになってから**読み込む（動的import）。ホーム・図鑑・カレンダー・記録はFirebaseを使わないので、その間は一番大きいデータベースの部品を読み込まない。読み込みに失敗しても、端末の中だけで動く画面はそのまま使える
- `onSnapshot`やログイン状態の見張りは、読み込みを待たずに呼べるよう`lazyWatch()`でくるんである。戻り値の「やめる関数」はすぐ返り、読み込みの途中でやめた場合も、終わった時点で止まる
- `index.html`に`preconnect`を入れて、Firebaseの取得先への接続を先に始めておく
- Firestoreは端末の中にキャッシュを持たせている（`cloud.js`の`store()`で`persistentLocalCache`）。`getProfile` / `getPostsByUser` / `getPostsTaggedWith` / `getMembers` は第2引数に関数を渡すと、**端末に残っているぶんを先に渡してから**最新を取りに行く（`fromCache()`）。使えない環境ではそのまま通信を待つだけなので、動きは変わらない
- プロフィール（`renderUser()`）は、先に枠だけ出して、読めたものから埋めていく。名前とアイコンは`profileCache`にあればすぐ出て、プロフィール・その人の投稿・一緒に食べた記録・身内全員の4つは同時に読み始め、返ってきた順に描く（`drawHead()` / `drawFollowStats()` / `drawPosts()` / `drawTagged()`）。図鑑とカレンダーは公開設定を見てから出すので、投稿が先に届いた場合は`readyForPosts()`が立つのを待つ。フォロワー数は身内全員を読み終わるまで「–」にしておく。「自分の投稿」（`renderMyPosts()`）も同じ考え方
- プロフィールが重いのは、共有した記録が写真を投稿データの中に文字列として持っているため（1杯あたり100〜150KB）。段階表示とキャッシュで体感は改善したが、根本的に軽くするなら、投稿には小さいサムネだけを入れて大きい写真は分けて持つ作りに変える必要がある
- ログアウトしてもFirestoreのキャッシュは端末に残る。読めるのはもともと身内全員に公開されている範囲で、キャッシュを使う画面はログインしていないと開けないため、そのままにしてある
- 自分の投稿には、右上の「⋯」（`.post-kebab`）から「編集」「削除」を選べる。一覧・投稿詳細・プロフィールのどこに出ている自分の投稿でも同じメニューが使える（`postCard()` が投稿者と自分のuidを比べて出し分けている）
- 「編集」は、投稿のもとになった端末側の記録を `postId` から逆引きして、その記録の編集画面（`renderEdit`）を開く（`editSharedPost()`）。共有中の記録を保存すると、みんなの記録の側にも自動で反映されるため、住所を含めて全部の項目をこの1画面でまとめて直せる。もとの記録が端末に見当たらない場合（別の端末で書いた場合など）は編集できない旨を伝える
- 「削除」はその場でみんなの記録から消す（`deleteSharedPost()`）。端末側の記録は残り、共有中の印だけが外れる
- お店の住所は、記録の編集画面（新規記録でも同様）で、既存のお店を選んでいるときに出る「住所」欄から直せる。ここで変えるとお店自体の住所が更新され、その記録を共有していればみんなの記録側にも一緒に反映される。他の記録・他の人が見ている投稿はそれぞれ記録した時点の住所を個別に持っているため、ここでは変わらない
- 「おすすめの一杯」は、ホームのギルチキのセリフに他の一言と同じ扱いで混ざる（`recommendOne()` の結果を `chikiTalk()` の候補にひとつ足しているだけなので、毎回出るわけではない）。そのセリフが選ばれたときだけ、下に「くわしく見る」のリンクが出て `#/recommend` へ飛べる
- 系統は `GENRE_RULES` のキーワードで、メニュー名とお店の名前から自動で判定する（`genreOf()`）。手直しはできない。当てはまらなければ「その他」として、おすすめの集計からは外れる
- 直近30杯を系統ごとに集計し、3杯以上ある中で平均点が一番高い系統を「アツい系統」とする。その系統の中から、お店・メニューの組み合わせごとに最高点と最終来店日をまとめ、2週間以上食べていないものの中で一番点数が高かったものを本命として選ぶ（`recommendOne()`）。記録が10件に満たない、アツい系統が見つからない、しばらく食べていない候補がない、のいずれかならおすすめは出ない
- `#/recommend` には本命のほかに、同じ系統の他の候補（点数順に最大4件）も出す
- 「まだ行っていない近くの店」は図鑑画面の上部から。Google Places API（Text Search (New)）で現在地周辺の「ラーメン」を検索する（`searchNearbyRamen()`）。- 図鑑にある店名と近そうなものには「済」の判子（`.nearby-stamp`）を重ねる。図鑑の来店回数の印と対になる朱色で、傾きも揃えてある。判子はマップへのリンクの上に重なっているので、押されたときはリンクに伝わらないよう止めてから、`KNOWN_STAMP_TALK`からランダムに選んだギルチキ口調の一言を出す。判定は`looksKnown()`で、カタカナ・ひらがなの違いは吸収し、「ブタ」と「豚」のように表記そのものが違う場合も、文字の重なり具合が7割以上あれば同じお店とみなす。完全一致ではないので、多少の誤判定はある
- 使っているAPIキーは `PLACES_API_KEY`。Google Cloud側で「Places API (New)のみ」「このサイトのみ」に制限してあるので、コードに直接書いてある。キーを作り直したらここを書き換える
- 課金を避けるため、呼び出すfieldMaskは`id`・`displayName`・`formattedAddress`だけに絞ってある（評価や写真を含めると単価の高い区分に上がってしまうため）。それに加えて、Google Cloud側の割り当てとは別に、アプリ側でも1日の呼び出し回数を絞っている（`NEARBY_DAILY_LIMIT`、端末ごとに `chiki` ストアの `nearbySearchUsage` に記録）
- お知らせ（更新内容の掲示板）はホーム右上のベルから `#/news`。内容は `app.js` の `CHANGELOG` 配列。未読の数はベルの右上に出る
- 未読の判定は「いちばん上の version を読んだか」だけで数えている（`newsUnreadCount()`）。既読の印は `chiki` ストアの `newsRead`。一度も開いたことがない端末では、古い記録を全部未読にすると驚かせるので、いちばん新しい1件だけを未読として数える
- アプリを開いたとき（と、ほかのアプリから戻ってきたとき）に版を調べ、古ければ画面全体をふさぐ更新の画面を出す（`checkVersionGate()` / `showUpdateGate()`）。「アップデート」を押して更新するまで中は触れない
  - 以前は消せるお知らせの帯を出すだけで、裏では `sw.js` が勝手に新しいファイルに入れ替えていたため、使う側から見ると「いつの間にか新しくなっている／押しても何も起きない」で、更新されたのかどうかが分からなかった
  - 調べられなかったとき（オフラインなど）はふさがない。そもそも更新できないため
  - 戻ってきたときの確認は5分に1回まで（`lastVersionCheck`）
  - GitHub Pages側のキャッシュがしばらく古いままだと、更新しても版が変わらず入れなくなってしまう。そのため同じ版に対して2回押しても変わらなかったときだけ「今回はこのまま使う」を出す（押した回数は `localStorage` の `ramen-log:update-try`。無事に新しくなったら消す）
- フォローは、プロフィール画面のフォローボタンから（自分以外の人にだけ出る）。フォロー中の相手は自分のプロフィールの`follows`配列に覚える（`cloud.saveProfile()`でmerge保存。ミュートの`mutedUids`と同じ仕組み）
- プロフィールにはフォロー中・フォロワーの件数を出す。フォロワー数は`cloud.getMembers()`で全員分を読み、`follows`にその人が入っている数を数えている（フォローされた側には何も書かないので、片方向の書き込みだけで済む）。押すと`#/follows/uid?type=following|followers`の一覧へ飛び、そこから各プロフィールへ行ける
- 「みんなの記録」は、フォローが1人以上いるときだけ画面上部に「みんな」「フォロー中」のタブが出る（`feed-tabs`）。フォロー中タブは、フォローしている人の投稿に加えて自分の投稿も表示する。絞り込みはFirestoreへの問い合わせを変えず、届いた投稿をその場で（クライアント側で）振り分けているだけ。開くたびに必ず「みんな」から始まる（`feedTab`を毎回'all'に戻している）
- セキュリティルールは `firestore.rules`。フォローの保存は、プロフィールの本人書き込み権限（既存のルール）でそのままカバーされるので、ルールの変更は不要。このファイルはソースには含まれず、Firebaseコンソールの「Firestore Database」→「ルール」タブに貼り付けて使う。身内のメールアドレスを `isAllowed()` の一覧に追加しないと、ログインできても読み書きできない

- 画面の切り替えには番号（`navSeq`）を振っていて、読み込みに時間がかかる画面は、待っている間に別の画面へ移っていたら結果を描き込まない（`navGuard()`）。以前はプロフィールの読み込み中にホームへ戻ると、あとからプロフィールが描き込まれ、URLはホームのままなので戻れなくなっていた。**新しく画面を足すときは、`await` のあとで `app.innerHTML` に書く前に `if (!alive()) return;` を入れる**
- 「自分の投稿」（`#/myposts`、`renderMyPosts()`）は、自分が共有した記録の一覧。自分のプロフィールとアイコンのメニューから開ける。新しい順・点数順・ギルティ順で並べ替えられる。一覧のギルティ・写真の拡大・長押しは `wirePostList()` にまとめてあり、プロフィールの「一緒に食べた記録」でも使っている
- 「ギルチキについて」（`#/about-chiki`、`renderAboutChiki()`）はガチャ画面から開く。文章は `ABOUT_CHIKI` を書き換える。ガチャの確率やポイントは設定値（`RARITY_WEIGHT` / `FEED_REWARDS` / `GACHA_COST`）から計算して表示するので、設定を変えれば自動で合う
- 設定画面は「アカウント・共有」「通知」「データ」「アプリ」「その他」のまとまり（`.set-group` / `.set-card`）に分けてある。上の項目名を押すとその場所まで送る（URLの#は画面の切り替えに使っているので、ジャンプはスクロールだけで行う）

## 通知（プッシュ通知）

- 4種類。**誰かが新しく共有したとき**（自分以外の全員に）、**自分の投稿にギルティが付いたとき**、**自分の投稿にコメントが付いたとき**、**誰かにフォローされたとき**。どれも設定画面の「通知」から、種類ごとにオン・オフできる（`notifyOnPost` / `notifyOnGuilty` / `notifyOnComment` / `notifyOnFollow`。プロフィールに保存。何も設定していない人は「受け取る」扱い）
- フォローの通知は、フォローした人のプロフィール（`users/{uid}`）が更新されたときに `follows` に増えた相手を探して送る（`notifyOnFollow`）。外して付け直すたびに飛ばないよう、同じ人から同じ相手への通知は1日1回まで。タップするとフォローしてくれた人のプロフィールが開く
- 仕組みは3段階。①端末が許可されたら、Googleが発行する宛先（トークン）を自分のプロフィールの `fcmTokens` 配列に覚える。②Firestoreに投稿・ギルティ・コメントが書き込まれた瞬間に、`functions/index.js` のCloud Functionsが自動で動く。③そこから該当する人の `fcmTokens` 宛てにFirebase Cloud Messagingで送る
- 届いた通知の表示はFirebaseのSDKが自動で行う。送るデータに`notification`（タイトルと本文）が入っていると、SDKが勝手に画面に出してくれるため、**`sw.js`側で`onBackgroundMessage`から`showNotification()`を呼んではいけない**（呼ぶと1件の通知が2つ表示される。実際に一度これで二重表示になった）。`sw.js`がやっているのは`firebase.messaging()`で受け取り口を用意することと、タップされたときにどの画面を開くかだけ
- iPhoneでは、**ホーム画面に追加したアイコンから開いていないと通知を許可できない**（iOS 16.4以降が必要）。Safariのタブのままでは、設定画面に通知の項目自体が出ない（`cloud.notificationsSupported()`で判定）
- 送れなかった宛先（機種変更などでもう無効になったトークン）は、Cloud Functions側で自動的にその人のプロフィールから消える（`sendAndClean()`）
- 通知を有効にする処理は`enableNotificationsNow()`に1つだけまとめてあり、設定画面とお知らせ画面のどちらの「通知を有効にする」ボタンからも同じものを呼んでいる。お知らせ画面の呼びかけは、まだ有効にしていない人にだけ出て、一度有効にすると消える
- Cloud Functions（Eventarc）は「同じ出来事を最低1回は届ける」仕組みなので、まれに同じ出来事が2回届くことがある。`claimEvent()`で、その出来事の`event.id`を`_processedEvents`コレクションに先に置けるかどうかを確かめ、すでにあれば（＝2回目以降）何もしない。このコレクションは記録用に増え続けるだけで、アプリ自体は参照しない
- iPhoneのWeb Push通知は、タイトルと本文以外のほとんど（アイコン・グループ化・通知音）を無視する仕様になっている。アイコンは常にアプリのアイコンになり、通知音も端末の標準音で固定。これはアプリ側では変更できない、Apple側の制限
- **`app.js`の`VAPID_KEY`は、Firebaseコンソールで発行してから貼り替える必要がある**（プロジェクトの設定→Cloud Messaging→ウェブ構成→鍵ペアを生成）。`__VAPID_KEY__`のままだと、通知の設定自体が「準備中」と出て使えない
- `functions/`はGitHub Pagesとは別物で、Firebase CLIというツールを使ってパソコンから直接Firebaseに配信する（`firebase deploy --only functions`）。詳しい手順は別途チャットで案内している

## パソコンで動かしてみる

`index.html` をダブルクリックして開くだけでは動きません（`app.js` の読み込み方式の関係）。
次のどちらかで開いてください。

**方法A：VS Code を使う（おすすめ）**
1. VS Code で `ramen-app` フォルダを開く
2. 拡張機能「Live Server」をインストール
3. `index.html` を右クリック →「Open with Live Server」

**方法B：Python を使う**
```
cd ramen-app
python -m http.server 8000
```
ブラウザで `http://localhost:8000` を開く。

※ Chrome の開発者ツール（F12）→ 左上のスマホアイコンで、iPhoneサイズの表示を確認できます。

## iPhoneで使えるようにする（GitHub Pages・無料）

1. [GitHub](https://github.com) でアカウントを作る
2. 右上「+」→「New repository」で新しいリポジトリを作る（Public を選ぶ）
3. 「Add file」→「Upload files」で、このフォルダの中身をすべてアップロード（`icons` フォルダも）
4. リポジトリの「Settings」→「Pages」→ Branch を `main`、フォルダを `/(root)` にして「Save」
5. 数分待つと `https://ユーザー名.github.io/リポジトリ名/` で開けるようになる

※ 公開されるのはアプリのプログラムだけです。記録したデータはiPhoneの中にだけ保存され、アップロードされることはありません。

## iPhoneのホーム画面に追加する

1. iPhone の **Safari** で上のURLを開く
2. 共有ボタン（□に↑）→「ホーム画面に追加」
3. 以降は **必ずホーム画面のアイコンから** 使う

> Safari のタブで記録したデータと、ホーム画面のアプリのデータは別々に保存されます。
> 記録はホーム画面のアイコンから始めてください。

## アプリを更新したとき

配信は今まで通り、ファイルをGitHubに上げた時点で全員に届く。バージョン番号を上げるかどうかで「更新の画面を出すかどうか」を決める。

**知らせなくていい細かい修正のとき**：ファイルをそのままGitHubにアップロードするだけでいい。`CACHE_NAME`・`APP_VERSION`・`CHANGELOG`はどれも触らない。更新の画面は出ず、次に開いたときから静かに新しくなる。

**お知らせしたい更新のとき**：
1. `sw.js` の `CACHE_NAME` と `app.js` の `APP_VERSION` を、同じ値に上げる（例：`ramen-log-v36` → `ramen-log-v37`）
2. `app.js` の `CHANGELOG` のいちばん上に、同じ version で更新内容を1件足す
3. 変更したファイルを GitHub に上書きアップロード
4. iPhone でアプリを開くと更新の画面が出るので、「アップデート」を押す。押すまで中には入れない。設定の「アプリの更新」から確認しても同じ画面が出る

## みんなの記録をまとめて消したいとき（リリース前のリセットなど）

Firestore のコレクションは `posts`（中に `comments`）・`users`・`_notifiedOnce`（通知の二重送り防止用）の3つ。
消すときは `ramen-functions` フォルダで Firebase CLI を使う。`--recursive` を付けないと `comments` が残る。

```
firebase firestore:delete posts --recursive --project maze-log-6ac46
firebase firestore:delete _notifiedOnce --recursive --project maze-log-6ac46
```

`users` を消すとニックネーム・アイコン・フォロー関係・通知の設定と通知トークンが消える（ログインアカウント自体は Authentication 側なので残る）。
アカウントごと消すときは Firebase コンソールの Authentication から。

端末側（IndexedDB）の記録は Firebase とは別の場所にあるので、消えない。
自分の端末だけ空にするときは、ホーム画面のアイコンを削除してから入れ直す（先に設定の「バックアップを作成」で書き出しておくと戻せる）。

`posts` を消すと、みんなの端末には「共有済み」の印（`records.postId`）だけが残る。
これは `reconcileSharedLinks()`（自分の投稿の画面を開いたとき）と、記録を編集して保存したときの `not-found` の受け止めで自動的に外れるので、
消す前に全員が v44 以降になっていれば手当ては要らない。

## データについての注意

- 記録はiPhoneの中にだけ保存されます
- ホーム画面のアイコンを削除すると、記録も一緒に消えます
- 機種変更に備えて、ホームの「バックアップ・設定」からときどき書き出してください
  （共有シートで「"ファイル"に保存」を選ぶと iCloud Drive などに保存できます）
